# Data provenance

This audit runs against **GiBleed**, the default teaching dataset of the OHDSI
[Eunomia](https://ohdsi.github.io/Eunomia/) package: a small, fully synthetic
OMOP CDM v5.3.1 instance of 2,694 patients generated by
[Synthea](https://synthetichealth.github.io/synthea/).

## The dataset is *not* committed to this repository

GiBleed is public and synthetic, so redistribution carries no privacy risk — but
patient-shaped data is not vendored here on principle. In the federated OHDSI model,
data stays at its source and only code and aggregate results move; a repository that
fetches its data rather than bundling it mirrors that norm and keeps the repo small.
The `results/*.csv` files are aggregate query output (counts, not patients) and *are*
committed, so every claim can be checked without loading the source data.

## How to obtain it

**Option A — via the Eunomia R package (what the notebook does).** On first call,
Eunomia downloads GiBleed, assembles a local SQLite database, and returns a connection:

```r
install.packages(c("Eunomia", "DBI", "RSQLite"))
library(Eunomia); library(DBI)
con <- dbConnect(RSQLite::SQLite(), getEunomiaConnectionDetails()$server())
```

**Option B — directly from OHDSI's public dataset repository.** The raw CSVs live at
[OHDSI/EunomiaDatasets](https://github.com/OHDSI/EunomiaDatasets):

```
datasets/GiBleed/GiBleed_5.3.zip
```

Unzip to recover one CSV per OMOP table (`PERSON.csv`, `CONDITION_OCCURRENCE.csv`, …),
which can be loaded into any SQL engine.

## Provenance, confirmed from the data itself

The `cdm_source` table stamps the dataset's origin — recovered in the audit *after*
the design was reconstructed from output alone:

| Field | Value |
|---|---|
| Generator | Synthea synthetic health database |
| CDM holder | OHDSI Community |
| ETL | [OHDSI/ETL-Synthea](https://github.com/OHDSI/ETL-Synthea) |
| CDM version | v5.3.1 |
| Source release date | 2019-05-25 |
| Vocabulary version | v5.0 (18-JAN-19) |
| Description | "synthetic, realistic (but not real)" |

## One portability quirk that matters

Eunomia's SQLite stores dates as **Unix-epoch integers**, not the CDM-specified
`DATE` type. Verify the column before doing arithmetic on it (a sample value looks like
`1443744000`, not `'2015-10-02'`). Every age calculation therefore uses:

```sql
strftime('%Y', condition_start_date, 'unixepoch')   -- SQLite
-- EXTRACT(YEAR FROM condition_start_date)           -- PostgreSQL
-- YEAR(condition_start_date)                         -- SQL Server
```
